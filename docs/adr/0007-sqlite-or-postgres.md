# SQLite or Postgres, chosen by DATABASE_URL

The app runs on SQLite (the default, ADR 0005) or on Postgres, whichever `DATABASE_URL` names: a `postgres://` URL means Postgres, anything else SQLite. Both are supported, rather than moving to Postgres, so self-hosters keep the single-box setup and anyone who wants a real database server can have one. Deployment is containers only: `compose.postgres.yml` adds a Postgres service over `compose.yml`. See `docs/research/postgres-migration.md`.

Drizzle has no schema that spans dialects, so:

- **Twin schemas.** `src/db/schema.sqlite.ts` and `src/db/schema.pg.ts` (and the two auth schemas) are the same tables column for column. `src/db/schema.ts` hands the app the one its database needs, typed as SQLite's, and the pg `db` is cast to the same `Db` type. `src/db/schema.test.ts` fails when the twins drift in tables, columns, keys or indexes, and `tsc` fails when their row types do.
- **Two migration histories**, `drizzle/sqlite` and `drizzle/pg`, both generated by `npm run db:generate`. A schema change is written twice.
- **Portable queries only.** No driver result shapes: a write that needs its count uses `.returning()`. JSON is compared as data, never as text, because `jsonb` reorders keys.
- **Transactions behave as if each ran alone on both.** SQLite keeps the per-process queue from ADR 0006. Postgres runs them at SERIALIZABLE and reruns one that fails with a serialization failure or deadlock (up to 10 tries with jittered backoff; a racing unique key shows up as a serialization failure too), so a transaction callback must not have side effects outside the database.
- **Tests run on both.** `npm test` uses SQLite, and with a Postgres `DATABASE_URL` it runs every test in its own database on that server. CI runs unit and e2e tests on both.

Amends ADR 0005 (the database is no longer SQLite only) and ADR 0006 (libsql for SQLite, node-postgres for Postgres; the queue is SQLite's only).
